# Events and replay

Source of truth: architecture D3. `data/events.jsonl` is the record; `data/state.json` is a cache rebuilt by replay and can be deleted at any time.

## Event line

```json
{"v":1,"t":"2026-10-03T17:42:10Z","type":"attempt","item":"maths/U349/g","topic":"1MA1/R9","correct":false,"sure":true,"answer":"4.5","seed":8812}
```

- `v` is the event-version for that `type`. A shape change bumps `v` and adds a reducer case; old lines are never rewritten.
- `type` is one of: `session` · `attempt` · `retest` · `teachback` · `intake` · `xp` · `squad` · `photo` · `usage` · `case` · `coach`. `usage` carries a model job's token counts, because the monthly token count needs an event and no other type holds tokens. It carries `estimated: true` when the provider reported no usable token counts and the provider estimated them. `case` is one detective-case answer with its 1 to 3 bet. `coach` is one of Dan's wrong steps and whether the pupil caught it (`wrong` is the bank's wrong answer, never the right one); the server writes it after the correction's `attempt`. Add to the union in `src/events/types.ts` first; `tsc` fails until the parser table and the reducer table both have the new `type@v` key.
- A `(type, v)` shape may be edited in place until the first GitHub release whose build can append it; after that, a change is a new `v`.
- `t` is UTC from `src/mcp/clock`, never the browser clock. `appendEvent` stamps it; a caller's `t` is overwritten. A `t` that is not a real date (`2026-02-30`) is refused.
- `appendEvent` writes only the fields `KEYS` lists for that `(type, v)`; a stray caller field (a correct answer) never reaches the log. `tsc` fails if `KEYS` misses a field of the type.
- Only `src/events/append.ts` writes under `data/`. It fsyncs per line, opens with `O_NOFOLLOW`, writes owner-only files, and refuses any path whose realpath is outside `data/` (`../`, absolute paths, symlinks, dangling symlinks). Only writers create `data/`; readers treat a missing folder as empty. The scripts take no path: they use `data/` in the folder they run from.
  `writeDataFile` (atomic: a fresh `O_EXCL` temp file created `0600`, fsync, rename; a leftover `.tmp`, symlink or not, is removed first, never written through) is the writer for every other file there: `state.json`, `config.json`, `profile.json`, `squad/<squad>/<pupil>.json`. `makeDataDir` makes a subfolder one level at a time, each level realpath-checked before anything is made inside it; `listDataDir` lists one folder's regular files and names what it skipped (a symlink, a subfolder).
- `photo.file` is relative to `data/` and must resolve inside it; `appendEvent` refuses the event otherwise, before anything is created.
  `writeIntakeFile` saves a photo's bytes as `data/intake/<name>` through `writeDataFile` (owner-only); the name must be letters, digits and `-` with a `.jpg`, `.png` or `.webp` extension, and an `intake` that resolves outside `data/` is refused.
- `photo@1` = `{item, topic, file, seed?, marks?, of?, clean?}`. `seed` is a `#gen` item's seed. `marks`, `of` and `clean` come together when the photo was marked (`marks ≤ of`, `of ≥ 1`) and are all absent when it is stored and not marked yet. `clean` = every presentation line (answer, units, sense) earned. Edited in place on 2026-09-29 (T13): no GitHub release existed, so no build could have appended the old shape.
- `job@1` = `{job, reason}`: one model call that fell back, for the parent digest. `defineJob` writes it once per fallback verdict (not per try), with the job name and a reason from `JOB_REASONS`; `no-model` is a choice and is not written. Never posted: `/api/event` and MCP `write_event` refuse it.

## Routes

`POST /api/event` takes a body without `t`, resolves a U-code in `topic` and `topics[].topic` to the topic id, and appends through `appendEvent`; a refusal is 400 and writes nothing, not even `data/`. It refuses an `xp` body (the tutor writes XP), a `photo` body (the tutor saves photos and their marks), a `job` body (the tutor records its own failed model calls) and a `retest` whose `passed` disagrees with `passes(score, of)` (2 of 3 or better, `src/flow/ladder.ts`). After an `attempt`, `retest` or `teachback` it appends that event's `xp` line (10, 20, 15, `XP` in `src/flow/xp.ts`); a failed xp append is logged and the response is still 201. `GET /api/state` is `replay` of the log and refreshes `state.json` when it is missing or behind; an empty log creates nothing. `GET /api/config` returns `{configured, config: publicConfig | null, weeklyTarget, presets}`; `POST /api/config` validates and saves through `saveSetup` (400 carries only its sentence, never a submitted field). `GET /api/usage` is `{month, tokens, cap}` for the London month, the same key replay uses. `GET /api/digest` (and `?day=`) is `{now, last}`, the `Digest` (`{week, title, lines}`, `src/digest.ts`) for the day's ISO week and the week before. A view whose day is in the real current week rewrites `data/digest/<iso-week>.md` for both weeks through `makeDataDir` and `writeDataFile`; a `?day=` in another week writes nothing, and an empty log creates nothing. The file name comes from `isoWeek()`, never from the request. `GET /api/next` (and `?day=YYYY-MM-DD`) is `nextStep` from `src/flow/next.ts`: `{day, flame: {week, days, target}, step}`, where `step` is `continue` (with the `end` body), `boss` (the `Boss` and a `start` body), `lesson` or `practice` (a topic and a `start` body), or `none`. The page posts those bodies verbatim. `GET /api/lessons` is `{ [topicId]: "/content/<subject>/lessons/<file>" }` for the topics whose lesson names their items file in `data-items` (`lessonFile`, now in `src/content/pack.ts`); read once per root. The map (`app/map.html`) posts the `start`/`end` bodies `/api/next` returns; the boss page (`app/retest.html`) posts the boss `start`, one `retest` per topic with `seed` = the boss seed, then the `end`. `GET /api/squad` (and `?day=`) is the week's `SquadView` from `src/api/squad.ts`; `POST /api/squad` takes `{week, answers: {answer, working}[]}`, marks the round again on the server, appends one `squad` event and then writes `data/squad/<squad>/<pupil>.json`; `POST /api/squad/join` writes `squad` and `pupil` into `profile.json`. `/api/event` refuses a `squad` body. `squad@1` carries `answers` (`{answer, working, correct}` per question; `score` is the count of `correct`). The pupil's squad file is a projection of the week's first `squad` event, written by `writeDataFile` after `makeDataDir` and rewritten by a same-week GET when missing or stale; a `?day=` GET for another week never writes. Friends' files in that folder are only read, and their answers are served only once the pupil's own `squad` event for the week exists. `GET /api/coach` (and `?day=`) is the tried topics and Dan's rank, or with `?topic=` the question side of the item Dan will try (`ready: false` with a `reason` otherwise; no write). `POST /api/coach` takes `step: "dan"` (runs `dan_wrong_step`, writes only its `usage` line; 409 once an attempt for the item and seed exists) or `step: "correct"` (marks on the server, appends `attempt` then its `xp` line then `coach`, and only then returns the working and the note). All live in `src/api/`, and `apiRoutes` in `src/server.ts` is the one route table.

Snap routes (O3, `src/snap.ts`, registered in `apiRoutes`). `POST /api/snap` (localhost) mints the one live snap for the last attempted item: 409 with no attempt, else 201 `{local, lan, qr, title, stem, expires}`. A new mint closes the old snap. `GET /api/snap?token=` is `{title, stem, figure?, model, state, result}`, where `state` is `open`, `marking` or `done`; 403 for a wrong or expired token. `POST /api/snap/photo` takes `{token, image: dataURL}`: the token first (403), then the bytes (JPEG, PNG or WebP by magic bytes, at most 5 MB, else 400), then it saves the file, answers 202 and marks in the background, then appends the `photo` event. One upload per token. The snap lives 15 minutes from the mint, moved to 10 minutes after an upload when that is later, and ends on a new mint or a restart. While a snap is open, a second listener is bound to the PC's private IPv4 address only (`lanAddress`). It serves `/snap.html` (token required), `/snap.js`, `/style.css` and the two snap routes behind its own Host, Origin and JSON check, and 404 for everything else, `/api/*` included.

## Config and profile

- `config.json` = `{v:1, preset, base_url, key, model, cap}` (`src/config.ts`). Owner-only; never sent to the browser. `publicConfig` is the only browser shape: no `key`, a `keySet` boolean instead. A missing or malformed file reads as not set up.
- `profile.json` = `{weeklyTarget, …}`: days a week with some practice (1 to 7). A save sets `weeklyTarget` and keeps every other key (later tickets add `board`). Joining a squad adds `squad` and `pupil`, both slugs (`slug` in `src/flow/squad.ts`: lower case, digits and dashes, no Windows device name), because both become path parts. T5 reads `weeklyTarget` for the flame in `/api/next`.

## Replay

`replay(lines) → State` in `src/events/replay.ts` is a pure reducer with one case per `(type, v)`. It reads no clock and no file. Lines are walked in file order, never sorted by `t`: a PC clock change can write an earlier `t` after a later one. Unreadable lines are skipped and counted, never fatal (a pupil may hand-edit the log). Every day, week and month is the London day of `t` (`localDay`), except a case, which is keyed by its own `day` field (the day it was picked for), not the London day of `t`. A leading byte-order mark is stripped. Every map in `State` has no prototype, so a topic or item id such as `__proto__` or `constructor` is an ordinary key.

State keys: `shape` (bump on a type change; now 6), `lines` (log lines it was built from), `skipped`, `hash` (sha256 of those lines), `topics` (id → `rung` 0–4, `nextDue`, `rag`), `xp` (`total`, `byWeek`), `flame` (ISO week → distinct days of real work), `confidentWrong` (item id → the pupil's wrong answer), `calibration` (ISO week → Sure/correct counts), `cases` (day → `kind`, `topic`, `item`, `bets` pairs of bet and correct in answer order; at most two pairs, the first answer and one re-ask), `caseSeed` (topic a confident-wrong case sends back tomorrow, or null), `tokens` (YYYY-MM → input + output), `session` (the open session `{mode, topic, t}`, or null; a start replaces an open one, an end closes whatever is open), `retests` (ISO week → summed re-test `score` and `of`, the guardrail's other half beside `xp.byWeek`, plus `taken` and `passed` counts for the digest), `coach` (`shown`, `caught` and Dan's `rank` from `rankFor` in `src/flow/rank.ts`; E3 reads `caught / shown`), `photos` (ISO week → `taken`, `marked`, summed `marks` and `of`, and `clean`; marks left on the table is `of − marks`, worked out by the reader), `failed` (ISO week → `job@1` reason → count; not practice, so no flame day).

Compatibility contract: `lines`, `topics[id].rung` and `xp.total` keep their paths across shape versions, or `project` in `src/events/check.ts` changes in the same PR. `hash` is read when present.

## Replay check

`replayCheck` (`src/events/check.ts`, CLI `scripts/replay-check.ts`) runs on start after an update:

- No readable `state.json`: rebuild from the log.
- Otherwise replay exactly the stored `lines` prefix with this build. Any rung below the stored rung refuses (exit 1, nothing written). Events appended after the last state write never trip it, so a real failed re-test is not a refusal.
- A log shorter than `lines`, or whose first `lines` lines no longer match `hash` (hand edit), rebuilds without refusing and lists every rung that fell. A stored `state.json` without `hash` cannot tell an edit from a code change.
- No log and no readable `state.json`: nothing is written.
- Every write first copies the old state to `data/state.prev.json`.

## Tests

One fixture per event version under `src/events/__fixtures__/`, enforced by a test over `EVENT_KEYS`. `replay.test.ts` asserts rung, next-due, XP, flame, calibration and tokens for the scripted six-week history (`six-weeks.jsonl`). Page code runs under `bun test` with `@happy-dom/global-registrator`, registered per test file (`src/marking/*-dom.test.ts`) and unregistered in `afterAll`; no preload. A DOM test imports its page with a `?dom` query so the unit test file's cached import of the same file does not stop the page code from running.
